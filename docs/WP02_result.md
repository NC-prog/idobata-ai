## A. カメラと「輪」

### 作ったもの

- **エッジ**（`edge/src/camera.ts`）: フロントから hello の後に届く `camera` メッセージの設定で、`getUserMedia({video:{640×360, 10fps}})` を開く。
  複数のカメラがあれば label に「Integrated」（`IDOBATA_CAMERA_LABEL`）を含むものを選ぶ。320×180 の JPEG（品質 0.7）を 5fps で送る。
  開けたかどうかを `camera_status` で知らせる
- **上りのバイナリに種別の 1 バイト**を付けた（`0x01` PCM、`0x02` JPEG。同じ WebSocket）。WP01 の契約からの変更
- **フロント**（`server/src/camera.py`）: 最新の 1 枚だけをメモリに持ち、YOLO11-pose（imgsz 320、FP16、ByteTrack）に掛けて輪を決める
  （`PartyTracker`。推論と切り離した規則だけなのでテストしやすい）。状態が変わったらエッジへ `{type:"party", state, count, facing}`
- **聞く・聞かない**: 発話区間の始まりか終わりに輪（PARTY）があるときだけ ASR に渡す。NONE／PRESENT の間は VAD は回すが結果を捨てる
- **別れと区切り**: 輪が NONE になった直後に「お気をつけて。またどうぞ。」を 1 会話 1 回（会話が始まっていたときだけ。
  `context/openers.yaml`）。NONE が `party.bye_sec`（8 秒）続いたら会話を区切る（来訪記録・話者の区別も消す）
- **アバター**: NONE は少しうつむいて視線を外す、PRESENT で顔を上げる、PARTY で相手（カメラ）を見る（待機・傾聴のときだけ上乗せ）
- **耳を塞がない安全装置**: フレームが `camera.stale_sec`（5 秒）届かなければ輪の判定をやめ、従来どおり聞く。
  `IDOBATA_CAMERA=0` ならカメラ無し（常に PARTY 扱い）
- **`--camera-debug`**: `/edge/debug` に、検出の矩形とキーポイントを重ねた最新の 1 枚（メモリのみ・LAN 内からだけ）と、
  `/edge/debug/party` に状態・人ごとの矩形の高さの割合・推論時間を出す

### 輪の判定（既定値）

| 設定 | 値 | 意味 |
|---|---|---|
| `party.min_box_ratio` | 0.35 | 矩形の高さ／画面の高さ。これ以上なら「近い」 |
| `party.face_center_tol` | 0.04 | 鼻と、左右の耳（片方でも見えなければ目）の中点の横のずれ／画面幅 |
| `camera.kpt_conf` | 0.5 | 鼻・両目が「見えている」とみなすキーポイントの信頼度 |
| `party.dwell_sec` / `leave_sec` | 2.0 / 3.0 | 輪に入る・外れるまでの秒数（見えなくなった人も 3 秒は輪に残す。トラックの切れ目で輪が揺れない） |
| `party.max_members` | 3 | |

**`min_box_ratio` の距離の校正はまだ**（人が 2〜2.5m に立って `/edge/debug/party` の `people` の値を見る必要がある）。
本物のカメラの前にいた人（距離は不明）は 0.35 を超えていた。

### 確認

**本物のカメラ**（`/dev/video0`、ヘッドレス Chromium。マイクだけ差し込み）:

- ブラウザが選んだカメラ: `Integrated Webcam`（640×360）
- カメラの前に人がいた（確認時に席にいた方）: `NONE → PRESENT`（14:29:31）→ **2.0 秒で `PARTY`**（14:29:33）、
  顔をそらして `PARTY → PRESENT`、正面に戻って再び `PARTY`
- **VRAM**: フロントのプロセス 294 MiB（CUDA の文脈込み。YOLO の割り当ては 45 MiB。予備枠 約 3.2GB に収まる。`imgsz` を下げる必要なし）
- **推論**: 中央値 **7.5ms**、95% 7.9ms（目標 20ms 以下）。受信 5.0fps
- 最初の測定では受信が 0.7fps しか出なかった。原因はヘッドレス Chromium の WebGL がソフトウェア描画（SwiftShader）で、
  VRM の描画がメインスレッドを埋めていたこと（50ms のタイマーが 2 秒で 11 回、`toBlob` 1.37 秒）。`--use-angle=gl` で
  Intel UHD（7560 の内蔵 GPU）を使わせると、タイマー 40/40 回、`toBlob` 8.6ms、描画 61fps、受信 5.0fps。
  **エッジのブラウザは GPU で描画させること**（D の設計書に書く）

**作った映像**（canvas の映像をカメラとして差し込み。人の写真は ultralytics の配布物にある `zidane.jpg`・`bus.jpg`。リポジトリには入れていない）＋差し込んだ音声:

| 確かめたこと | 結果 |
|---|---|
| 誰もいないときに部屋の会話（来訪者役の WAV）を流す | `輪が無いので、この発話区間は聞き取りません（NONE）`。ASR に渡さず、字幕も応答も無し |
| 人が来る（`zidane.jpg`） | **2.55 秒で PARTY**（滞留 2 秒＋フレーム間隔と処理） |
| 輪の中で話す | 聞き取り・応答あり。音声開始 **0.32 秒**（相槌）、LLM の 1 文目 0.66 秒（カメラを動かしたままで 1.3 秒未満） |
| 立ち去る（黒い画面） | 3.1 秒で NONE → 別れの一言 → **8 秒で会話を区切る**（`輪が無くなって 8 秒経ったため会話を区切りました`） |
| 2 人並ぶ（`bus.jpg`） | **count=2**（`zidane.jpg` は 2 人写っているが、片方の左目の信頼度が 0.45 で「正面」の条件に届かず count=1） |

**人が横を向いて 3 秒で外れること**は、本物のカメラの前の人で `PARTY → PRESENT` を確かめた（顔をそらした時刻の正確な記録は無い）のと、
ユニットテスト（横向き→ 3 秒で外れる）で確かめた。**部屋の会話をスピーカーから流す確認**は、音を出さず、
同じ音声をブラウザのマイクに差し込んで行った（輪の判定で捨てることの確認としては同じ。マイクとスピーカーの音響の経路は見ていない）。

## B. 話者の区別

### 作ったもの（`server/src/speaker.py`）

- 発話区間ごとに ECAPA-TDNN の埋め込み（192 次元）を取り、会話の中だけでオンラインにまとめる（重心とのコサイン類似度 ≥ 0.45 なら同じ人）。
  話者は `A`・`B`・`C`… の記号だけ。**埋め込みとまとまりはメモリだけ**。会話が区切れたら捨てる（待機タイムアウト・輪が解けて 8 秒・終了時）
- 声の長さが 1 秒未満の区間（「はい」）は埋め込みが不安定なので、新しい話者を作らず近い話者に寄せ、重心も動かさない
- **受け付けの規則**: 最初に現れたときに輪が PARTY → 相手、**NONE → 捨てる**（その後に輪の中で話しても捨てる）。
  **PRESENT（近づいてくる途中）→ 保留**、輪ができてから話せば相手（作業指示の「最初に現れた時刻に PARTY だったら相手」を少し緩めた。
  話しかけながら近づいてくる人を、その会話の間ずっと聞かないことにしないため）
- LLM には `A：〜` `B：〜` の形で渡す（履歴も同じ形）。システムプロンプトに「記号は名前ではない。応答に書かない」を足し、
  応答の頭に `A：` を付けてきたら外す
- 紹介状の聞き取り: 同意を言った人を主とし、別の人の答えも受け付けて、答えの後ろに「（付き添いの方の答え）」と付ける（職員に分かるように）
- 来訪記録に `speakers`（相手として受け付けた話者の数）を足した。文字記録の来訪者の行に `speaker_label`
- 埋め込みは ASR と並べて取る（応答の遅れにしない）

### モデルの速さ（2 秒の区間）

| 動かす場所 | 時間 | |
|---|---|---|
| CPU 4 スレッド | 中央値 116ms（負荷の高いときの別の測定で 102ms） | **目標の 50ms に届かない** |
| CPU 8 スレッド | 78ms | 届かない |
| **GPU（予備枠）** | **4ms**、割り当ての最大 119 MiB | これを既定にした（`speaker.device`、GPU が無ければ CPU） |

作業指示は「CPU で 50ms 以内のもの」だったが、候補（ECAPA は 3 つの中で最も小さい）で CPU 50ms 以内のものが無かった。
GPU の予備枠に約 120 MiB を足しても YOLO と合わせて 1GB に届かない。ASR と並べて動かすので、CPU でも応答は遅れない（`speaker.device: cpu` で切替）。

### しきい値（VOICEVOX の話者で実測）

1 秒以上の区間どうしのコサイン類似度: 同じ人 最小 0.37・中央値 0.64、別の人 95% 0.56・中央値 0.17。
本人と付き添いが交互に 12 回話す並びを、実際のまとめ方に通した結果:

| 組 | 0.40 | **0.45** | 0.50 | 0.55 |
|---|---|---|---|---|
| 玄野武宏（男）／冥鳴ひまり（女） | 12/12 | **12/12** | 12/12 | 11/12（3 人に割れる） |
| 玄野武宏（男）／青山龍星（男） | 12/12 | **12/12** | 11/12 | 10/12 |
| 春日部つむぎ／ずんだもん（どちらも高い女声） | 0/12 | 0/12 | 0/12 | 9/12（4 人に割れる） |

**0.45** にした。VOICEVOX の似た声どうし（つむぎ／ずんだもん、類似度が最大 0.71）は分けられない。人の声での確認はまだ。

### 確認（`--edge`、作った映像＋差し込んだ音声）

誰もいないときに職員役（青山龍星）の声 → 人が来て PARTY → 本人（玄野武宏）と付き添い（冥鳴ひまり）が交互に 3 回ずつ → 会話の途中で職員役がもう一度:

```
輪が無いので、この発話区間は聞き取りません（NONE）     ← 職員の声。話者 A（輪の外）として覚える
新しい話者 B（相手、最も近い話者との類似度 0.28）       ← 本人
新しい話者 C（相手、最も近い話者との類似度 0.16）       ← 付き添い
（文字記録の話者）B C B C B C
輪の外で先に聞いた話者 A の発話なので、応答しません     ← 会話の途中の職員の声
```

ラベルは 6 回とも安定し、職員の声は 2 回とも捨てられた（1 回目は輪が無いので ASR にも渡さず、2 回目は話者で捨てた）。

## C. 能動的な切り出しと沈黙

### 作ったもの

- **切り出し**: 輪が PARTY になった瞬間に、時間帯の挨拶＋天気の一言＋開いた問い 1 つ（`server/context/openers.yaml`）。
  - 天気の一言: 気温の実況が 10 度未満なら「今日は冷えますね。」、30 度を超えれば「今日は暑いですね。」、それ以外は今日の予報の
    **最初の**天気（「晴れ　後　くもり　夜遅く　雨」なら晴れ）で「いいお天気／曇り空／あいにくの雨／雪」。`weather.json` が無ければ言わない
  - 問いは「お元気にされてました？」「今日はどちらまで？」「何かお困りのことはありますか？」「今日はどんなご用でした？」を会話ごとに順に回す
  - **LLM を通さない定型**で、切り出し・沈黙・別れの文は起動時に全部合成しておく（決まった文だけなので 15 件前後、数秒）
  - 1 会話 1 回。同じ会話の中で輪ができ直しても言わない。言った文は対話履歴に積む（LLM が挨拶を重ねたり、
    「お困りのことは」を繰り返したりしない。既存の規則がそのまま効く）
- **沈黙**: PARTY のまま、最後に誰かが話してから（来訪者の発話区間の終わり、または案内役が言い終えてから）`party.silence_sec`（7 秒）
  経ったら「ゆっくりで大丈夫ですよ。」「ほかにも何かあれば、どうぞ。」を順に。1 会話 2 回まで。応答中・聞き取り中・電話番号の続きを待っている間は言わない
- **別れ**: A のとおり（輪が NONE になった直後に 1 回、8 秒で区切る）
- 切り出し・沈黙はカメラが動いているときだけ（カメラ無しのときは従来どおり、話しかけられてから答える）

### 確認（`--edge`、作った映像＋来訪者役の WAV）

人が来る（`zidane.jpg`）→ 切り出し → 来訪者が話す（`pair_honin_1_ja.wav`）→ 黙る → 立ち去る:

```
  0.39s 輪: NONE → PRESENT
  2.57s 輪: PRESENT → PARTY
  2.57s 輪ができたので切り出します
  2.57s [井戸端AI] こんにちは。
  2.57s 切り出しの音声開始: 輪ができてから 0.00 秒
  2.57s [井戸端AI] 今日はいいお天気ですね。
  2.58s [井戸端AI] お元気にされてました？
 12.22s [聞き取り:ja] 自分の介護のことで相談に来ました。
 12.90s [井戸端AI] 介護についてのご相談、ありがとうございます。
 14.09s [井戸端AI] 介護の相談は高齢介護課（2階）で受け付けていますので、お声がけください。
 14.82s [井戸端AI] このこと、担当の課に伝えておきましょうか？
 25.17s [計測] 発話終了→ ASR 0.28s / 相槌開始 0.28s / LLM 1文目確定 0.96s / 音声開始 0.28s / LLM 完了 2.15s
 32.30s 輪のまま 7 秒黙っているので、沈黙の一言を言います（1 回目）
 32.30s [井戸端AI] ゆっくりで大丈夫ですよ。
 39.97s 輪: PARTY → NONE
 39.97s 輪が解けたので別れの一言を言います
 39.97s [井戸端AI] お気をつけて。またどうぞ。
 48.15s 輪が無くなって 8 秒経ったため会話を区切りました
```

- **切り出しの開始は PARTY から 0.00 秒**（事前合成。目標 0.5 秒以内）
- 作業指示の「3 人（本人役の WAV＋カメラ前の人）」は、カメラの前の人を写真の映像で代えた（人が離席していたため）。
  **カメラの前に人が立つ確認は残っている**（切り出しの声が来訪者に自然に聞こえるか、近づく速さに対して 2 秒の滞留が長すぎないか）
- 気づいたこと: 沈黙の一言が、行為の提案（「伝えておきましょうか？」）の返事待ちのときにも出る（今回もそう）。
  返事待ちの沈黙には提案の聞き直し（既存の `reask`）のほうが合うかもしれない

- **設計書と手順書**: `docs/edge_pc_setup.md`（構成・IP・つながり方・secure context の方式・Chrome のポリシー・キオスクのショートカット・
  Windows の設定・フロントの設定・箱から出して 30 分の手順・うまくいかないとき）
- **方式は ②**（指定したオリジンだけを secure とみなす）。起動フラグ `--unsafely-treat-insecure-origin-as-secure` と同じことを
  Chrome のポリシー `OverrideSecurityRestrictionsOnInsecureOrigin` で入れるのを勧めた（警告バーが出ない・ショートカットを直されても効く）。
  カメラ・マイクの許可（`VideoCaptureAllowedUrls`・`AudioCaptureAllowedUrls`）と自動再生（`AutoplayAllowlist`）もポリシーで
- **フロントに足した設定**: `IDOBATA_EDGE_WS_HOST`（WebSocket の待ち受け。既定 127.0.0.1）と `IDOBATA_EDGE_ALLOW`（エッジにつないでよい IP・CIDR。
  この機体自身はいつでも可。空ならこの機体からだけ）。許可していない相手は `/edge/`（と `/`）が 403、WebSocket は close 4003。
  職員パネル・管理者ページは別（LAN 内＋パスワード）

### 確認（7560 の上で、LAN の IP でページを開いて別機の代わりにした）

フロントを `0.0.0.0` で待ち受け、`IDOBATA_EDGE_ALLOW=192.168.0.10`（この機体の LAN の IP）:

| 確かめたこと | 結果 |
|---|---|
| 許可した IP から `/edge/` | 200 |
| 許可していない相手（この機体の別のアドレス 100.93.x）から `/edge/` | **403** |

- **Windows 機での実測はしていない**（手元に無かった）。設計書の 8 章に残した

## E. 追加の修正（姿勢推定の置き換え・返事待ちの沈黙・chrome://gpu）

### E-1 姿勢推定を ultralytics（AGPL-3.0）から rtmlib（Apache-2.0）に

- **RTMDet-nano**（人の矩形、入力 320×320）→ **RTMPose-s**（COCO 17 点、入力 192×256）を rtmlib で動かす（`server/src/camera.py` の `PoseDetector`）。
  キーポイントは COCO 17 点のままなので、輪の判定（距離・正面・滞留）は変えていない
- **追跡**: rtmlib の `PoseTracker` は内部でトラック ID を持つが外に返さないので使わず、**簡易トラッカーを自前で書いた**（`SimpleTracker`）。
  前のフレームの矩形と IoU ≥ 0.3 の人を同じ人に（IoU の大きい組から）、残りは中心の距離が画面の対角の 0.15 以内で最も近い人に。
  15 フレーム（5fps で 3 秒）見えなければ忘れる。ID はセッション限り・メモリのみ
- **ONNX Runtime**: `onnxruntime-gpu`（CUDA。torch が入れた nvidia の CUDA・cuDNN を `preload_dlls` で使う）。CUDA が使えなければ
  警告を出して CPU で動く（`camera.device`）。rtmlib は CPU 版の `onnxruntime` を要求するが、GPU 版と同じ import 名で両方入ると壊れるので、
  `pyproject.toml` の `[tool.uv] override-dependencies` で CPU 版を外した
- `ultralytics`・`ultralytics-platform`・`ultralytics-thop`・`lap` は依存と `uv.lock` から外した（`torchvision` も外れた）
- **重みが無い・読めないとき**は姿勢推定を止め、**カメラ無しとして従来どおり聞く**（確認の途中で、重みが無いと推論の
  タスクだけが落ち、フレームは届き続けるので輪が NONE のまま＝ずっと聞かない状態になることが分かったので直した）

### E-2 計測（置き換え前後）

| | ultralytics（YOLO11n-pose、FP16） | **rtmlib（RTMDet-nano＋RTMPose-s、ONNX Runtime CUDA）** |
|---|---|---|
| 1 フレームの推論（単体、2 人の写真 320×180） | — | 中央値 **7.5ms**、95% 8.2ms（CPU なら 14.9ms） |
| 1 フレームの推論（動かしたまま、人なし） | 中央値 7.5ms（本物のカメラ） | 中央値 **4.4ms**、95% 5.0ms |
| 1 フレームの推論（動かしたまま、2 人。LLM・TTS も動いている） | 中央値 6.5〜7.3ms（1〜2 人） | 中央値 **8.9ms**、95% 9.8〜21.0ms |
| VRAM（姿勢推定だけの単体のプロセス） | 294 MiB（CUDA の文脈込み） | **174 MiB** |
| VRAM（フロントのプロセス全体。話者埋め込みの torch を含む） | — | **512 MiB**（姿勢推定を読めなかったときは 264 MiB＝話者埋め込みの分。差の約 250 MiB が ONNX Runtime） |

- 目標の 20ms 以下は中央値で満たす。2 人のときの 95% が 21.0ms になった回がある（RTMPose は人ごとに 1 回推論するので人数に比例する。
  LLM・ASR と GPU を分け合っている）。5fps（200ms 間隔）には十分収まる
- 予備枠（約 3.2GB）に対してフロントのプロセス 512 MiB

### E-4 提案の返事待ちの沈黙（`actions.Conversation.silence_reask`）

提案（PROPOSED）の返事待ちのまま `party.silence_sec` 黙ったら、沈黙の一言ではなく**提案の文をもう一度**（「このこと、担当の課に伝えておきましょうか？」）。
1 回だけで、2 回目からは黙って待つ（沈黙の一言の回数には数えない）。提案文は対話履歴の直前の応答の後ろに足す。

### E-5 chrome://gpu の確認

`docs/edge_pc_setup.md` には「うまくいかないとき」の表にしか無かったので、**30 分の手順の 18 分の行に足した**（キオスクではない普通の Chrome で
`chrome://gpu` を開き、WebGL・WebGL2 が「Hardware accelerated」であること。「Software only」ならドライバを入れ直す）。
