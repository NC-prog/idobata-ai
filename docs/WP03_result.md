## 2. 知識パック

### 2-1. 作ったもの

- `kb/build.py`: 取得 → 抽出 → チャンク → 人名除去 → 埋め込み → 保存
  - `kb/` は `server/` とは別の uv 環境。実行は `uv run --project kb python kb/build.py --site etajima`
  - `--weather-only`: 天気だけ更新する
  - `--from-cache`: 取得し直さず、キャッシュからチャンクを作り直す
- 出力は `~/idobata-data/kb/<site>/`（manifest.json / chunks.parquet / index.lancedb / weather.json）。`kb/pack/<site>` はそこへのリンク（git 管理外）
  - 作りかけを読ませないよう、別ディレクトリに作ってから差し替える
- `kb/sources/{etajima,akiota}.yaml`: クロール定義。`kb/README.md`: 使い方
- `deploy/standalone/kb-nightly.{service,timer}`（毎晩 2 時）、`kb-weather.{service,timer}`（5・11・17 時の発表の後）: systemd の user ユニットの雛形。**有効化はしていない**（人間が判断）
- `kb/tests/`（6 件）: チャンク、パンくず、除外、URL の正規表現、気象庁 JSON の整形（保存した実データ）、人名除去

### 2-4. 検索としきい値（実測）

- ハイブリッド: Ruri v3 のベクトル検索（LanceDB、上位 20）と、文字 2-gram の BM25（上位 20）を、順位の融合（RRF）でまとめる
- **しきい値**: Ruri v3 の cos 類似度は、関係のない発話でも 0.77〜0.84 になる（例: 「今日の天気は」→ PM2.5 の資料が 0.837）。一方、関係のある発話の資料はおおむね 0.85〜0.95 だが、「今週末、何かお祭りありますか」→ オータムフェスタは 0.824 だった。**ベクトルだけでは切れない**ので、2 段にした
  - 類似度 **0.86 以上**なら入れる
  - 類似度 **0.80 以上**で、かつ BM25 で **5 位以内**（語が実際に一致している）なら入れる
- 結果（上位 5・合計 1,000 字まで）:
  - 関係のある 12 発話: 10 件で資料が入った
  - 関係のない 9 発話: 7 件が「なし」
  - 資料が入った関係のない発話は 2 件: 「トイレ」→ 浄化槽の資料、「孫が来週」→ 1 件。どちらも害は小さい
  - 資料が入らなかった関係のある発話は 2 件: お祭り（今週末の行事が無い）、フェリー（時刻表は PDF）
- **検索時間: 中央値 9.9ms、最大 14.3ms**（21 回、CPU、Ruri v3 30m）。BM25 だけで拾った資料の類似度を LanceDB に問い合わせていたとき、資料なしのターンで 50ms かかった。メモリ上のベクトルで計算するように直した

### 2-5. 人名を入れない

- 分類での除外: パンくずに「議会・会議録・入札・契約・職員採用・人事・市長の部屋・秘書室・選挙・監査・合併協議会」を含むページを外す。タイトルの語でも外す
- それでも、住民向けのページの本文に氏名が残っていた（例: イベントの「▶MC」の下の出演者名、市長名、レシピの考案者、移住者の紹介）。**チャンクにする前に規則で「（氏名省略）」に置き換える**（`redact_names`）。規則は次のとおり
  1. 役職のあとに続く氏名（市長・院長・会長・代表・司会・講師・考案者など）
  2. 敬称・役職が後ろに付く氏名（さん・氏・様・先生・議員）
  3. 氏名だけを ／・、 で並べた行
  4. 伏せた氏名の直後の読み仮名・並べた名
  - 「市長が必要と認める書類」「保健医療課 宛」のような文は残す（テスト済み）
- 「えたじま観光アンバサダーの皆様をご紹介します」は、ページ全体が人物紹介なのでタイトルで外した
- **限界**: 機械的な規則なので、漏れも誤りもある。例えば「代表取締役社長 （氏名省略） 肇史」のように名だけが残る。逆に、規則に当たらない書き方の氏名は残る。**人間による抜き取り確認が要る**


## 3. 対話への組み込み

### 3-1. システムプロンプト（固定事実層）

- `src/persona.py` がテンプレート（`config.DialogueConfig.persona_template`）に facility を埋める。中身は次のとおり
  - 「あなたは江田島市役所の1階ロビーにいる案内役です。名前はまだありません。」
  - 【ここで分かっていること】: 場所・開庁時間・課と担当と階（別の建物の課は「この建物ではなく …」）・補足・緊急連絡先
  - 【話し方の決まり】
  - 【今日】: 日付・曜日・天気
- 指示書の骨子は「「{facility.name}」の{location_phrase}にいる」だった。location_phrase に施設名が入っているので「「江田島市役所」の江田島市役所の1階ロビー」と重なる。そのため location_phrase だけにした
- 【話し方の決まり】には、指示書の項目のほかに、評価で出た誤りに合わせて次を足した
  - 持ち物は参考資料にあるものだけ。無ければ「持ち物は（担当の課）でご案内します」とだけ言う
  - 建物の中の場所と道順は知らない（「近くの職員にお尋ねください」）
  - 観光地・店・行事の名前は参考資料か固定事実にあるものだけ。市の外の場所を市のものとして挙げない
  - 天気・気温は【今日】に書いてあることだけ
  - 緊急連絡先は名前と番号の両方を言う
  - 「参考資料」という言葉を口に出さない
  - 応答の長さは今のまま（2〜3 文の目安も今のまま）

### 3-2. 検索の呼び出しと出典

- 各ターン、LLM の前に知識パックを検索する（別スレッド、CPU）。`[計測]` に `検索 13ms` の形で出る
- **参考資料は、システムプロンプトではなく、最新の来訪者メッセージの頭に付ける**（`turn_template`: 【参考資料】… 【来訪者の発話】…）
  - 指示書の骨子はシステムプロンプトの末尾だったが、そこに置くと参考資料が変わるたびに、後ろの会話履歴まで vLLM のプレフィックスキャッシュが効かなくなった。2 往復目の初回トークンまで 0.5 秒以上かかった
  - 移したことで、システムプロンプトと履歴はキャッシュされる。LLM に渡る内容は同じ。履歴には発話だけを積む
- 出典: 参考資料があるターンだけ、応答の最後に「詳しくは市（町）のホームページにも載っています」と添えさせ、使った資料の番号を `[出典:1,3]` で書かせる
  - 印は読み上げ前に取り除く
  - 使った資料のタイトルを字幕の下に薄く出す（エッジへ `{type:"sources", titles}` を送る。契約への追加）
  - URL は読み上げない。text モードでは `[出典] タイトル` と表示する

### 3-3. 日本語の崩れ対策と、言わないことの安全装置

- 抑える: `temperature 0.5`、`presence_penalty 0.3`（`config.py`）
- 止める（文単位、TTS の直前）
  - **英字の連なり（3 文字以上）が許可語（`allow_ascii`、江田島は LINE）に無い文は、LLM に 1 回だけ日本語で言い直させる**。だめなら捨てて WARNING
  - 実機で「窓口でcheckしてから、formに記入」→「窓口で確認してから、申請書に記入」、「serviceはfree」→「サービスは無料」になった。JR（2 文字）はそのまま
  - 最終の評価 20 問で英字の混在は 0
- 指示書にない安全装置（評価で、プロンプトの決まりだけでは止まらなかったもの）
  - **来訪者に住所を聞き返す文は捨てる**（「お住まいの市区町村」など。`banned_phrases`）。国保の質問で「まずはお住まいの市区町村に確認して」が出た
  - **拠点の外なのに LLM が拠点のものとして挙げやすい場所を含む文は捨てる**（拠点 YAML の `outside_places`。江田島は宮島・厳島神社。「江田島のおすすめ」で 2 回続けて宮島を挙げた）。固定事実にも「宮島は廿日市市」と書いた
  - **緊急連絡先の名前を言って番号を言わなかったら、番号の文を足す**（「マイナンバー総合フリーダイヤルの番号は、0120-95-0178です。」）
  - **日本語以外の発話には LLM を通さず「申し訳ありません、外国語でのご案内は準備中です。」を返す**。プロンプトだけでは、英語の質問に日本語で中身を答えてしまった
  - プロンプトの見出し（【参考資料】）が応答に漏れたら「手元の資料」に言い換える
- 「がなくてしまった」のような活用の崩れは機械的には取れない。最終の評価では見当たらなかった。ただし文字化け 1 件（「高齤介護課」。中間の試行で 1 回）は出た

### 3-4. 速さ（音声開始 1.3 秒未満を保つ）

検索そのものは 10ms だが、参考資料が長いとプロンプトの前処理（prefill）が伸びた。

| 変更 | 内容 | 根拠（実測） |
|---|---|---|
| 参考資料の位置 | システムプロンプト → 最新の発話の側 | 履歴を含むターンで、キャッシュが効かず初回トークンまで 0.5 秒以上 |
| 参考資料の上限 | 1,500 字 → **1,000 字**（上位 5 件は同じ） | 初回トークンまで（キャッシュ外し、6 問の中央値）: 1,500 字 502ms / 1,000 字 343ms / 700 字 254ms / 資料なし 約 50ms |
| 1 文目を読点で切る最小字数 | 4 → **2** | 「ええ、最近は朝晩の冷えが…」（読点の前が 2 字）を 1 文丸ごと合成して音声開始 1.46 秒 |

計測（`[計測]`、疑似音声 `--input-wav`、変更後）: 音声開始 0.75 / 1.28 / 1.19 秒。エッジ（ヘッドレス Chrome に来訪者役の WAV を偽マイクとして流す）: **0.86 / 1.23 / 1.11 秒**。

- 参考資料ありのターンが 1.2 秒台で、余裕は少ない
- 参考資料を 1,000 字にしたことで、長い手続きの説明は切れやすくなる
- エッジ確認の途中で、**7560 のデスクトップの Chrome に `/edge/` のタブが開いたまま**（`edge-sga0uzgj`）で、それもフロントにつながっていた。音声を聞くのは最後に hello したエッジなので、ヘッドレスの方を読み直して確認した
